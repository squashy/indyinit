# Battle for the 92: spec

Indy Init, November 7. Build runs 9:00 AM to 5:00 PM from an empty public repo. This repo's first commit is the plan and question bank; everything that runs is built during the contest.

## Why we are building this

Indiana fourth graders study state history. Their [grade 4 social studies standards](https://secure.in.gov/doe/files/Indiana-Academic-Standards-Grade-4-Social-Studies.pdf) include events like the Battle of Tippecanoe, yet history that happened in their own county rarely gets a turn. Here it decides a game: a student who knows their county earns more armies.

AI can write that content quickly, and it can be confidently wrong. In our practice prototype, about 15% of 508 facts written with high confidence needed correcting or rewording. Children should not learn from that, so our fact pipeline is built to be measured: we plant fake questions, two AIs from different vendors check every question independently, and the answer key is published so anyone can verify the score.

## What we are aiming for

| Rubric | Our answer |
|---|---|
| **The Build** | Live game judges can play, with the repo, tests, pipeline and board on show |
| **Wildcard** (primary) | A swing: a fact-checked conquest game for any state, generated by a factory, with fakes planted to test the AI |
| **Community Impact** (primary) | Hoosier fourth graders and their teachers, starting with all 92 counties |
| **Software Factory** (how we built it) | Tickets become agents' pull requests, gates decide what ships, and new states need no code. This is the story, not the entry |

**Primary user:** an Indiana fourth grader on a school Chromebook or a phone, in class. **Second user:** their teacher, who needs to trust the facts and can see each fact's source.

## What we commit to

- **Indiana** is the pilot and gets the most polish.
- **Six proving states** show the factory works: Ohio, Louisiana, Wyoming, Michigan, Virginia and Texas. `STATES.md` says what each one tests.
- **Every other state is a bonus**, and must pass every gate.

## How the team works

Two people, several tools. Both operators' agents pull the next unblocked ticket from a traverseit.io board, so ownership comes from tickets, not people. Claude Code, GrokBot and Cursor cloud agents all follow `AGENTS.md`. Because Claude's hooks do not run for the other tools, CI is what enforces every rule.

## Phases

Each phase ends when its check passes. Times are in `RUNBOOK.md`, and tickets are in `BOARD.md`.

### 1. Foundation
Repo, Vercel project, CI, and every gate in `BARS.md`, failing for the right reason before any game code exists.
**Done when:** a deliberately bad pull request is blocked, and its preview still builds.

### 2. Game core
Designer and dev work in parallel from `CONTRACT.md`.
**Done when:** rule tests, simulation and rule-breaking checks pass on Indiana's map with test questions, and one turn plays in a real browser.

### 3. Fact pipeline
Two independent checkers process about 50 Indiana questions into verdicts, and a merge step applies the ship rule.
**Done when:** the key holder has scored the sample.

### 4. Indiana, live
All 92 counties checked, gaps filled, quiz reward and fairness tuned, all gates green, deployed.
**Done when:** a person can play it at the production URL and Indiana has a score.

### 5. Proving states
Run each as one ticket with the same prompt. Fix the factory, never the state. Every fix is a row in `FAILURES.md`.
**Done when:** six states pass with no state-specific code.

### 6. Bonus states
Pull more state tickets until the 4:15 PM freeze.

### 7. Evidence and demo
Lock verdicts, score, publish the key, fill `SCORECARD.md`, finish Devpost, rehearse.

## Pipeline for one state

1. Generate the map from the state's manifest, with machine-drawn regions and any crossings from `STATES.md`.
2. Run checker A and checker B on the state's bank questions, separately.
3. Merge verdicts. Ship only what both confirm. Send disagreements to a person; anything unresolved at freeze is rejected.
4. The content agent fills counties below the minimum and writes explanations. Every new fact goes through both checkers.
5. Tune the state: quiz reward, second-player armies and game length (`BARS.md`).
6. Run all gates, then open the pull request. CI repeats the browser check against the preview.
7. A person looks at the regions in the preview, reads 15 random questions and all flagged items, then merges.
8. The key holder scores the state.

## Out of scope today

Accounts, servers, online multiplayer, cards, runtime AI calls, and the six jurisdictions with too few counties (`STATES.md`). Students' data never leaves the device.

## What comes next

Told plainly to judges: put it in front of a real fourth-grade class and measure whether they learn; map questions to the state standards; give teachers a view of each fact's source; add finer map units for small states.
